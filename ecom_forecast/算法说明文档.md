# 电商单量预测系统 — 算法说明文档

---

## 一、整体思路：为什么要分三层？

想象你是一个老经理，要预测明天仓库要发多少货。你不会直接拍脑袋猜，而是：

1. **先看大盘**：整家店今天大概多少单？（宏观把握）
2. **再拆渠道**：淘宝货架贡献多少？直播贡献多少？联盟达人贡献多少？（细化拆分）
3. **最后分仓**：这些单各发哪个仓？（落地执行）

这个系统就是把这个思路写成代码，分三层递进预测，大促前还可以叠加第四层人工校准：

```
历史订单数据
     │
     ▼
┌─────────────────────────────┐
│  第一层：全局模型            │  → 预测"整店今天多少单"
│  (GlobalBaseModel)          │
└────────────┬────────────────┘
             │
             ▼
┌─────────────────────────────┐
│  第二层：渠道子模型          │  → 把整店单量拆到各渠道
│  (ChannelEnsemble)          │     货架 / 直播 / 联盟
└────────────┬────────────────┘
             │
             ▼
┌─────────────────────────────┐
│  第三层：分仓路由            │  → 每个渠道的单发哪个仓
│  (WarehouseRouter)          │     昆明仓 / 武汉仓 / 湖州仓
└────────────┬────────────────┘
             │
             ▼
┌─────────────────────────────┐
│  第四层：预售校准（可选）    │  → 预售截止后用真实定金单量
│  (PresaleAdjuster)          │     精校尾款期的仓库备货数
└─────────────────────────────┘
```

## 二、核心算法：LightGBM 梯度提升树

### 2.1 用大白话解释"决策树"

决策树就像一串"是/否"判断题：

```
今天是周末吗？
  是 → 是大促尾款爆发期吗？
         是 → 预测 12000 单
         否 → 预测 5000 单
  否 → 昨天单量超过 3000 吗？
         是 → 预测 3500 单
         否 → 预测 2000 单
```

一棵树判断能力有限，所以 LightGBM 用**几百棵树接力**，每棵树专门修正上一棵树的错误，最终叠加得到精准预测。这叫**梯度提升（Gradient Boosting）**。

### 2.2 为什么选 LightGBM 而不是普通随机森林

| 对比项 | 随机森林 | LightGBM（本系统） |
|--------|----------|-------------------|
| 建树方式 | 并行建多棵树，每棵独立 | 串行建树，后树修正前树误差 |
| 精度 | 中等 | 通常更高 10-20% |
| 训练速度 | 中等 | **极快**，用直方图算法压缩数据 |
| 内存占用 | 大 | 小 |
| 对大促异常值的处理 | 一般（平均投票） | 好（可配置样本权重放大大促数据） |
| 可解释性 | 稍好 | 也提供特征重要性 |

> **结论**：在电商时序预测场景，LightGBM 是行业主流首选，精度和速度都优于随机森林。

### 2.3 损失函数选的是 MAE（L1）

模型优化目标是让预测值和真实值的**绝对误差**尽量小，而不是平方误差（MSE/L2）。

原因：电商大促时单量会暴涨几十倍（异常大值），如果用 L2，模型会被这些极端值"吓到"，过度向大促倾斜。L1 对极端值更鲁棒，日常预测不会被大促数据带偏。

## 三、特征工程：给模型喂什么"食材"

特征工程是整个系统最重要的部分——模型学得好不好，80% 取决于喂进去的特征质量。

### 3.1 时间特征（告诉模型"现在是什么时候"）

| 特征 | 含义 | 例子 |
|------|------|------|
| `day_of_week` | 星期几 | 3 = 周四 |
| `is_weekend` | 是否周末 | 1/0 |
| `month` | 月份 | 11 = 11月 |
| `dow_sin / dow_cos` | 星期的正弦/余弦编码 | 让"周日→周一"的跳变变平滑 |
| `month_sin / month_cos` | 月份的正弦/余弦编码 | 让"12月→1月"的跳变变平滑 |

> **为什么要用正弦/余弦编码？** 普通编码里"周日=6，周一=0"，模型会以为它们差距很大，但实际上紧挨着。正弦/余弦把数字排成圆形，头尾自然相连。

### 3.2 历史销量特征（告诉模型"过去卖了多少"）

**滞后特征**（Lag）= 往前看 N 天的实际单量：

```
今天预测值 ← 昨天单量(lag1) + 7天前单量(lag7) + 14天前单量(lag14) + 28天前单量(lag28)
```

**滚动均值/标准差**（Rolling）= 近 N 天的平均水平和波动幅度：

```
roll_mean7  = 过去7天日均单量（近期趋势）
roll_mean30 = 过去30天日均单量（中期基准）
roll_std7   = 过去7天波动幅度（今天异常否？）
```

**同比特征**（YoY）= 去年同一时期的单量：

```
yoy = 去年同一周（±3天平均）的单量
```

> 注：用 ±3 天范围取均值，是因为大促日期每年会浮动（如 618 预售可能提前也可能推后）。

### 3.3 大促特征（最关键！电商预测的灵魂）

这是本系统和普通时序模型最大的差异所在。

#### 基础大促标记

| 特征 | 含义 |
|------|------|
| `is_preheat` | 今天是预热期（大促前7天） |
| `is_presale` | 今天是预售期（用户付定金阶段） |
| `presale_day_index` | 预售期第几天（1=第一天，0=非预售期）越到后期定金越趋于稳定 |
| `is_campaign_day` | 今天是大促正式期（双11/618等） |
| `is_final_payment` | **今天是尾款爆发期**（大促开始后 0~2 天，>95% 尾款集中于此） |
| `final_payment_day_offset` | 尾款期第几天（1/2/3，0=非爆发期）配合支付分布特征 |
| `is_post_campaign` | 今天是售后期（大促后7天，退款高峰） |
| `days_to_nearest_campaign` | 距最近大促还有几天（负=还没到，正=已过去） |
| `campaign_intensity` | 大促强度分（0~1） |

强度分的设计如下：

```
大促正式期：1.0（最高）
预售期：    0.3 → 1.0（随时间渐增）
预热期：    0.2 → 0.3（轻微提升）
售后期：    0.3 → 0.0（逐渐消退）
60天以外：  0.0（完全无影响）
```

> **新增 `is_final_payment` 的意义**：大促期通常持续 3~7 天，但尾款爆发集中在前 3 天，之后是退款和售后。原来的 `is_campaign_day` 把整个大促期一刀切，模型难以区分"爆发日"和"收尾日"。现在单独标注尾款爆发期，模型可以精确学到每天不同的量级节奏。

### 3.4 渠道专属特征

#### 直播渠道（event）特征

直播渠道特征分为三层，从当天信号到预售窗口信号：

**① 当天直播信号**

| 特征 | 含义 |
|------|------|
| `has_live` | 今天是否有直播 |
| `anchor_tier_code` | 主播档级（A头部=3 / B腰部=2 / C尾部=1） |
| `expected_viewers` | 预计观看人数 |

**② 短期/中期点滞后信号**

| 特征 | 含义 | 设计原因 |
|------|------|---------|
| `live_lag1` | 昨天是否有直播 | 自播连播效应，今天有人回访 |
| `live_lag7` | 7天前是否有直播 | 预售期一般7~15天，7天前的直播=定金日直播信号 |
| `live_lag14` | 14天前是否有直播 | 捕捉更长预售期（如双11预售最长15天） |
| `anchor_tier_lag7/14` | 7/14天前主播档级 | 头部主播预售场带来的定金量在尾款日爆发 |
| `viewers_lag7/14` | 7/14天前观看人数 | 流量规模直接对应预售期订单规模 |

> **核心逻辑**：预售专场直播发生在尾款日前 7~15 天。订单日期用的是尾款支付时间，所以尾款爆发日的 `live_lag7/14` 就代表"当时预售场有多强"——这是预测尾款峰值最直接的前置信号。

**③ 预售窗口聚合信号（7~15 天回望）**

| 特征 | 含义 | 区别 |
|------|------|------|
| `presale_has_live` | 过去7~15天内是否有任何直播 | 有/无信号 |
| `presale_max_tier` | 过去7~15天内最高主播档级（含所有直播） | 整体流量上限 |
| `presale_live_tier` | 过去7~15天内**仅预售专场**的最高主播档级 | **更纯净的预售信号** |
| `presale_total_viewers` | 过去7~15天内预计总观看人数 | 整体流量规模 |

> `presale_max_tier` vs `presale_live_tier`：日常自播频繁的店铺，`presale_max_tier` 长期偏高（日常直播拉高了值），会误导模型以为每天都是大促前夕。`presale_live_tier` 只统计标注了"是否预售场=1"的场次，在没有预售专场时归零，信号更纯净。

#### 联盟渠道（affiliate）特征

| 特征 | 含义 |
|------|------|
| `commission_rate` | 当月佣金率（影响达人推广积极性） |
| `active_affiliates` | 当月活跃达人数 |

### 3.5 预售单量专项特征（全渠道通用）

这组特征从订单数据的 `是否预售单` 标记列中提取，反映**该渠道对预售的历史依赖程度**。

| 特征 | 含义 | 作用 |
|------|------|------|
| `presale_orders_roll_max30` | 近30天最大日预售单量 | ≈ 上次大促峰值，最强的规模信号 |
| `presale_orders_roll_sum90` | 近90天累计预售单量 | 跨大促周期的规模趋势 |
| `presale_camp_ratio` | 近30天预售单占总单比例 | 渠道预售依赖度（0~1），高=该渠道主要靠大促 |
| `presale_orders_lag7` | 7天前预售单量 | 检测相邻大促溢出（部分尾款推迟支付） |
| `presale_orders_lag14` | 14天前预售单量 | 同上 |

> **为什么不用 `lag365`（去年同期）？** 因为 `order_count_yoy` 已经覆盖了去年同期总单量，而且大促日期每年浮动，用 ±3 天的 yoy 已经足够。`presale_orders_roll_max30` 的"上次大促峰值"方案更直接，不依赖日期对齐。

## 四、样本权重：让模型重点学大促

大促天数少（全年约 40~60 天），日常数据占多数。若不加权，模型会"讨好"日常数据，在大促期误差很大。系统采用**三级权重**：

```
普通日（日常）          权重 ×1.0
大促期 / 预售期         权重 ×3.0   （数据少但重要，加强学习）
尾款爆发日（有标注）    权重 ×4.5   （is_presale_order=1 或 is_final_payment=1）
```

**三级加权的逻辑：**

- 尾款爆发日是大促中最难预测、对仓库备货影响最大的日子
- 有 `is_presale_order=1` 标注的行是最精准的监督信号（人工确认了这单来自预售）
- 对这些行给予最高权重（基础大促权重 × 1.5），让模型集中火力学习尾款爆发规律

## 五、训练流程详解

### 5.1 数据切分（时序交叉验证）

```
│←────────── 训练集（历史数据）──────────→│←─验证集（最近30天）─→│
2022-01-01                            今天-30天            今天
```

> **注意**：时序预测不能随机打乱数据做交叉验证！必须严格按时间顺序：用过去预测未来，绝不能用"未来"数据去训练。

### 5.2 Early Stopping（防止过拟合）

训练过程中，每建一棵树都会在验证集上测一次误差：

```
第1棵树：  验证集误差 5000
第2棵树：  验证集误差 4800  ← 变好了，继续
...
第300棵树：验证集误差 1200  ← 最好
第301棵树：验证集误差 1220  ← 变差了
...
第350棵树：验证集误差 1250  ← 连续50次没改善，停止！
```

`early_stopping_rounds=50` 意味着：连续50棵树没有改善验证集误差，自动停止，取第300棵树的结果。这避免了树太多导致"死记硬背"历史数据（过拟合）。

### 5.3 第三层：分仓路由（统计学习，非机器学习）

路由层不训练机器学习模型，而是**直接统计历史仓分布比例**：

```
学习阶段：
  统计"稳定期"（规则变更后、排除大促应急期）的历史数据
  昆明仓分到 40%？武汉仓 35%？湖州仓 25%？
  → 记住这个比例

预测阶段：
  渠道预测总单量 × 各仓历史比例 = 各仓预测单量
```

**过滤"脏数据"的三重保护：**

1. 排除规则变更日期之前的全部数据（老规则已作废）
2. 排除规则变更前后各 7 天（过渡混乱期）
3. 排除大促应急调仓时段（临时分流不代表正常规则）

## 六、预售校准层（第四层）：用已知信息修正预测

### 6.1 使用时机

大促预售截止前 1~2 天，定金订单数已基本确定，此时：

- 模型的估算误差可能达 20~30%（因为预售场规模每年不同）
- 但**真实定金单量已知**（系统可查）
- 用真实数量反推尾款期入仓量，精度可从 ~25% MAPE 提升到 ~8%

### 6.2 核心公式

```
仓库入仓订单（第d天）= 定金订单数
                      × 尾款转化率        （默认 88%，即 12% 用户不付尾款）
                      × (1 - 退货率)      （默认 5%）
                      × 尾款支付分布[d]   （第1天65%、第2天20%、第3天10%、第4天5%）
```

**参数说明：**

| 参数 | 默认值 | 含义 |
|------|--------|------|
| 尾款转化率 | 88% | 付了定金最终完成尾款的比例 |
| 退货率 | 5% | 尾款支付后最终退货的比例 |
| 净入仓率 | 83.6% | = 转化率 × (1 - 退货率) |
| 支付分布[1] | 65% | 尾款开启当天就支付的比例（大部分用户立即支付） |
| 支付分布[2] | 20% | 第2天补款 |
| 支付分布[3] | 10% | 第3天长尾 |
| 支付分布[4] | 5% | 第4天及以后 |

### 6.3 与模型预测的融合方式

系统支持**加权融合**，不强制完全替换模型预测：

```
融合预测 = 校准值权重 × 预售校准值
         + (1 - 校准值权重) × 模型预测值

权重=1.0：完全采用校准值（定金数可靠时推荐）
权重=0.5：各取一半（对定金数不完全确定时）
权重=0.0：纯模型预测（不启用校准）
```

### 6.4 支付分布的历史学习

如果有往年大促仓库订单数据，系统可以**自动从历史学习支付分布**，替代默认值，使参数更贴近本公司实际情况。

## 七、订单日期的关键约定：用尾款时间

这是预售场景最容易踩坑的地方。

| | 定金支付时间 | 尾款支付时间（本系统采用）|
|---|---|---|
| 何时入仓 | ❌ 不入仓，定金期仓库无动作 | ✅ 尾款付完才下推仓库 |
| 单量峰值 | 直播当天（预售专场播出日） | 尾款开启日 +1~4 天 |
| 对仓库的指导意义 | 误导备货节奏 | 与实际履约节拍对齐 |

**两张表各司其职：**

```
直播排期表 → 日期 = 直播/预售场发生的日期
              特征工程自动向前移位 7~15 天
              生成 presale_live_tier / live_lag7/14 等特征

渠道订单表 → 日期 = 尾款支付时间（入仓时间）
              is_presale_order = 1（标注这单来自预售）
```

## 八、评估指标说明

| 指标 | 公式 | 含义 | 目标 |
|------|------|------|------|
| **MAPE** | 平均\|预测-实际\|/实际 × 100% | 平均偏差百分比 | < 15%（大促期 < 20%）|
| **Bias%** | 平均(预测-实际)/实际 × 100% | 系统性高估/低估 | \|Bias\| < 5% |
| **RMSE** | √均方误差 | 绝对误差大小（同量纲）| 越小越好 |

**大促期和非大促期分开评估**，因为大促时单量是平时的 5~10 倍，混在一起算会掩盖日常预测的真实水平。

**预售校准后单独评估**：启用校准层后，单独统计尾款爆发期（is_final_payment=1）的 MAPE，直观展示校准带来的改善幅度。

## 九、算法横向对比：有没有更好的选择？

### 9.1 主流算法大比较

| 算法 | 优点 | 缺点 | 适合场景 |
|------|------|------|---------|
| **LightGBM（当前）** | 快、精度高、支持自定义特征、可解释 | 需要手工特征工程 | ✅ 电商时序，有大促日历 |
| **随机森林** | 简单稳定、不容易过拟合 | 精度通常低于 LightGBM 10-20%，速度慢 | 数据量小、特征少时可用 |
| **XGBoost** | 和 LightGBM 同类，成熟稳定 | 速度稍慢，内存占用大 | 可替代 LightGBM，差别不大 |
| **Prophet（Facebook）** | 自动处理季节性、节假日，零代码 | 精度较低，不支持多维特征（渠道/仓库） | 快速出基线，单序列预测 |
| **LSTM/Transformer（深度学习）** | 理论上能学复杂时序规律 | 需要大量数据（>3年）、难调参、不可解释 | 数据量极大时可尝试 |
| **ARIMA/指数平滑** | 经典统计，可解释性极强 | 无法处理多变量、大促效应 | 传统零售，无活动干扰 |
| **TFT（Temporal Fusion Transformer）** | 业界 SOTA，支持多变量+注意力机制 | 极难实现，需要 GPU，调参复杂 | 超大规模、有算法团队时 |

### 9.2 对本系统的具体评价

**当前选择（LightGBM）是合理的，理由：**

- ✅ 电商场景数据量中等（通常 1~3 年），LightGBM 的甜点区
- ✅ 大促特征可以手工注入，比自动学习更可控
- ✅ 训练一次只需几分钟，运营可以频繁重训
- ✅ 特征重要性可以输出，出了问题能排查
- ✅ 行业内头部电商公司（阿里、京东）的供应链预测也大量使用 GBDT 系列
- ✅ 预售校准层可以在模型精度不足时用规则兜底，双重保障

**有提升空间的地方：**

| 方向 | 当前做法 | 可改进为 | 预期收益 |
|------|----------|---------|---------|
| 直播预售精度 | 用排期特征（预售场标注） | 接入实时直播间在线人数 API | 大促直播预测 MAPE 降 3-5% |
| 支付分布学习 | 默认值或手动输入历史数据 | 从每次大促后自动更新分布参数 | 校准层逐年变精准 |
| 同比特征 | 去年同周 ±3 天均值 | 用动态时间规整（DTW）匹配相似大促周期 | 节日浮动年份改善 |
| 不确定性估计 | 只给点预测 | 改用分位数回归输出 P10/P50/P90 | 让运营知道"最坏情况备多少货" |
| 超参数调优 | 手动设置 | 用 Optuna 自动搜索最优参数 | 精度提升 2-5% |
| 模型集成 | 单模型 | LightGBM + XGBoost + 线性模型加权平均 | 降低方差，提升稳定性 |

### 9.3 什么情况下应该换算法？

| 情况 | 建议 |
|------|------|
| 数据少于 6 个月 | 换 Prophet 或指数平滑（数据不够 LightGBM 吃饱） |
| 有实时流数据 | 换在线学习算法（如 Vowpal Wabbit） |
| 需要概率预测 | 改为分位数 LightGBM 或 DeepAR |
| 平台超过 20 个 | 考虑 Temporal Fusion Transformer |

## 十、一句话总结

> 本系统用 **LightGBM + 精心设计的电商特征**（大促日历、尾款爆发期标注、预售场直播滞后信号、预售单量规模特征）训练三层预测模型，并在大促截止后叠加**预售校准层**用真实定金数二次修正。在中等规模电商数据下是**精度、速度、可维护性**综合最优的方案。随机森林可以作为对比基准，但预期精度会低 10-20%。未来随数据积累可引入分位数预测和自动调参来进一步提升。
