# 预期GMV

入口：侧边栏「预期GMV」，路由 `/expected-gmv`，API `/api/expected-gmv`。

## 解析和复核

通过已登录的 `lark-cli` 用户身份只读 Wiki 和电子表格。链接必须包含 `sheet` 参数，默认读取 `A1:CZ140`，来源设置可调整范围与年份。使用 CLI 返回的真实 `row_indices` / `col_indices`，拒绝截断结果。无需修改已有直播排期同步配置。

天猫按「渠道目标-GMV」至「核心指标」区域定位五个渠道，分别保存日目标和原表汇总。排除整个 GMV 区域均为空的月末模板日期；月份内的日期必须完整，单个渠道缺值报错，零值正常保留。活动保留官方/店铺节奏原文、所在日期列、子类、源单元格；当前不推断合并范围或原文中的精确起止时间。

二次核验是“代码读取范围核验”，不设置独立金额核验页面。宿主从原始快照重新定位 GMV 区域边界、日期表头、五个渠道行、每日及汇总列、官方/店铺节奏，逐项核对候选代码实际引用的源单元格及原值，检测错位、误读销售/去年区域、日期错列、渠道互换、漏读或多读。原表月合计、双11合计与日目标有差异不会导致解析失败，也不改原表。

每次读取均生成新的解析版本，保存来源快照、源版本、哈希、规则版本、结果及核验报告。读取失败、规则失败、读取范围核验失败分开记录；范围不正确的结果不能启用。

## AI规则维护

初始规则分别在 `api/gmv_rules/tmall.py`、`api/gmv_rules/douyin.py` 与 `api/gmv_rules/douyin_baby.py`，宿主解析器分开实现。每个店铺创建独立规则标识，并选择相应解析模板初始化，既有规则不能切换解析器。规则是受限 Python 代码，只允许 `RULE = 字典字面量`；用 `ast.literal_eval` 解析，绝不 `exec` 或导入 AI 代码。支持渠道别名、表头行、冲突行覆盖和单位换算，固定 GMV 业务边界及五类渠道。新的表格结构若超出这些声明能力，需要开发者扩展宿主解析器，AI 会失败并保留旧规则。

只有最新一次初始规则解析失败（`parse_failed`）或读取范围核验失败（`verification_failed` 且 scope 为 `source_ranges`）、尚未消耗修复机会、当前规则未变更时，才可启动更新。飞书读取失败不能触发。每个店铺同时只允许一个维护任务。

维护模型先通过实际图片输入/JSON输出测试，再读取当前代码和绑定飞书表格，然后写候选规则并验证。表格相对失败快照发生变化时要求先重新解析。工具仅四项：`read_rule`、`read_sheet`、`write_rule`、`validate_rule`；没有 shell、任意文件或通用 CLI 能力。宿主固定飞书命令和参数。候选路径必须严格等于宿主生成的文件名，只能写规则目录；启用后的不可变规则另存版本目录。

独立模型请求作为读取范围审查任务，无写权限，重新接收原始来源、修改前后代码、候选代码实际执行结果及历史回归结果。审查模型必须按当前店铺契约，从原表独立认定各渠道及活动/排期的全部源单元格，返回每项目标对应的范围依据 JSON；天猫为五渠道及两类节奏，抖音为三渠道及达人意向排期。派生汇总引用的源坐标按日源单元格去重。宿主比较这些坐标与代码实际读取坐标，缺项、重复、错位或只有“通过”而无范围依据均拒绝。审查失败、格式异常、超时、工具预算耗尽、历史回归变化均拒绝启用。通过后宿主再次回归并以当前版本比较方式启用，自动重解析原快照。默认维护 DeepSeek、审查 MiniMax，可分别选择提供方。任务日志只呈现动作、工具输入输出、代码和决策摘要，不展示隐藏思维链。

页面每2秒轮询任务，所有步骤保存。服务重启时将未完成任务标记中断。历史成功快照参与回归；回滚会创建新版本并复核历史成功数据，不删除任何历史。已有解析结果保留当时规则归属，回滚后需要重新解析产生新结果。

## 模型与存储

默认 `deepseek-flash`（`https://api.deepseek.com/chat/completions`）和 `MiniMax-M3.1-Flash`（`https://api.minimax.io/v1/chat/completions`），模型名可配置。官方说明：<https://api-docs.deepseek.com/guides/vision/>、<https://platform.minimax.io/docs/api-reference/text-openai-api>。接入采用 OpenAI 兼容消息格式与工具调用。工具上下文保留厂商完整 assistant 消息；日志剥离隐藏推理。维护与审查各自调用前检查真实多模态输入与结构化输出，工具参数及规则代码在写入前验证。

在模型设置保存 API Key，复用集成设置 Fernet 加密能力，接口不回显密钥；留空保持原值。也支持 `DEEPSEEK_API_KEY`、`MINIMAX_API_KEY` 环境变量。加密密钥位置遵循现有 `INTEGRATION_SETTINGS_KEY_FILE` 配置。尚未提供密钥时可正常读取和解析，但不能调用真实模型；「验证模型」检查已保存配置，会产生少量模型调用。

独立 SQLite/WAL 存储在 `ecom_forecast/data/expected_gmv/history.sqlite3`，可用 `GMV_DATA_DIR` 指定位置。备份时同时保留数据库、加密密钥和规则目录。当前任务协调使用单进程锁；部署保持单个 Uvicorn worker，不支持多进程同时更新规则。面向本机桌面使用，继承现有系统访问控制。

验证：`python script/test_expected_gmv.py`；`cd frontend` 后 `npm run build`。测试使用 `script/fixtures` 中真实表格的只读快照，模型交互用模拟响应覆盖审查拒绝与成功启用；真实模型验证须先配置密钥。

MiniMax 区域：国内密钥选择 `china`（`https://api.minimaxi.com/v1/chat/completions`），国际密钥选择 `international`（`https://api.minimax.io/v1/chat/completions`）。测试按钮先保存当前表单再验证；变更区域不需要重新填写已有密钥。HTTP 错误展示状态码和脱敏后的服务说明，401 提示检查密钥与接口区域。

## 天猫货架实际达成

“货架-常规”下方展示实际单量、实际GMV、实际客单价、GMV达成率四行。只读查询 `dwh_db_order_summary`，固定 `order_status=900`、`platform IN (TB,TM)`、`shop_name=薇诺娜天猫旗舰店`、`channel_type=店铺`。按 `order_create_time` 的日期汇总，使用起日包含、截止次日不包含的时间范围，覆盖日内时间。实绩与飞书解析历史分开，查询当前只读库，不写历史目标快照。

客单价＝实付金额总和/单量总和，区间采用加权计算；达成率＝实际实付GMV/货架-常规目标。日、月、总计与双11区间分别按对应日期计算，未来或无记录日期为缺失，不补0。区间以有数据的日期累计，提示最近日期与记录天数。源值NULL保留缺失；单量为0时客单价为空，目标为0时达成率为空。底部五渠道合计只统计目标行，不混入实绩、单量、客单价或比例。其他店铺不会复用这一固定店铺查询。API：`GET /api/expected-gmv/runs/{run_id}/shelf-actuals`。测试：`python script/test_gmv_actuals.py`。

页面初始加载展示进度；网络或服务端错误最多自动重试2次，最终失败显示持续错误提示和“重新加载”按钮。刷新失败保留已有目标。实际数据有单独的失败提示和重新读取入口，区分无源记录与请求失败。

百补实际达成：在“百补”目标下同样展示四行实绩，固定 `channel_type=百亿补贴`，其余店铺、状态、平台口径保持一致。百补GMV达成率以百补目标为分母。现有实际数据接口增加 `channels`，分别返回货架-常规和百补，保留原货架 `periods` 字段兼容；两个渠道按条件分别汇总，不互相混入。

达播实绩：限定 `channel_type=达播` 后，以 `channel_name=李佳琦` 归入达播-超头，以 `channel_name<>李佳琦 OR channel_name IS NULL` 归入达播-二梯队，沿用状态900、TB/TM和指定店铺条件。两组互斥，空名称归其余组；各自展示单量、实付GMV、加权客单价及对应目标的GMV达成率。接口 `channels` 增加两个达播组，合计仍只统计原五个目标行。

CPS实绩：`channel_type` 前3字符为CPS的记录归入货架-CPS（SQL使用 `SUBSTR(channel_type,1,3)=CPS`，与用户的 `LEFT(channel_type,3)=CPS` 同义），包含各CPS前缀子渠道。其余状态、平台、店铺及日期条件沿用用户指定口径；达成率以货架-CPS目标为分母。

底部汇总区按列展示三项：预期GMV合计、实际GMV合计、实际单量合计。预期只累计五个目标；实际分别累计五渠道的实付金额及单量，不累计客单价或达成率。某渠道无源记录时不参与已有实绩合计，全部无数据时显示缺失；若有源记录但所求字段缺失，则该项合计显示缺失。每日与原表区间汇总同步切换。

## 抖音独立解析

来源：内容电商by月日指标 → 调整10-11（sheet=9k30mr），默认范围 A1:Q200。单独的 douyin 规则版本和 `gmv_douyin_parser.py` 读取“日期在行、渠道在列”的结构；不复用天猫渠道映射。业务渠道为抖音自播（D列）、抖音商城（原表“商城汇总”，E列）、抖音达播（F列）；不将内容电商、抖音全店或快手列纳入渠道合计。

原表明确标注“纯销维度，GMV=纯销/0.7预估”。保留原始纯销值，按该系数转换GMV，页面持续显示口径说明及来源提示。日目标覆盖2026年10月1日至11月30日，共61天；每渠道另从日目标计算10月、11月及总计，192条目标记录。独立核验从原表标签重定位日期和渠道，拒绝错读快手、缺失日期、错误年份或系数、原值缺失。

右侧表头与内容位置不完全相符，按实际内容读取K列意向档期、L列合作类型、M列达人、N列预估支付GMV（万元），共8条达人意向排期。复合/备选日期保留原文，不推断成交日期；万元金额转元单独保留，不混入日目标。该表未提供官方/店铺节奏，界面展示达人意向排期并说明来源边界。

展示沿用日期为列、渠道为行，预期/实际对比色、底部汇总及历史快照。抖音自播已接入独立四店自营直播间实绩查询；商城已按自营其他/自营短视频接入，达播已按达人短视频/达人直播间/达人其他接入；实际合计包含自播、商城、达播三个渠道。不使用天猫实绩口径；后续渠道按用户提供SQL独立扩展。`python script/test_douyin_gmv.py` 覆盖换算、源范围、排期、派生汇总、规则隔离与禁止读取天猫实绩。

## 抖音自播实绩接入

根据新增用户SQL，汇总以下四店：抖音-薇诺娜官方旗舰店、抖音-薇诺娜旗舰店、抖音-薇诺娜护肤旗舰店、抖音-薇诺娜护肤旗舰店2。固定订单状态900、渠道自营直播间；不额外增加用户未指定的平台条件。按天求SUM(order_qty)、SUM(order_pay_amount)，客单价使用总实付/总单量，达成率以抖音自播预期GMV为分母。缺少AND的原SQL已在参数化查询中补齐，日期为半开区间以覆盖当天全部时间。

日/月/总计复用正确的日期范围加权汇总。通用接口 `GET /api/expected-gmv/runs/{run_id}/actuals` 按店铺选择实际查询，旧shelf-actuals路径保留兼容。抖音商城、达播均已按下面口径接入，底部实际合计包含自播、商城、达播，页面明确说明；天猫实绩仍按原五渠道统计。

抖音商城实绩：沿用指定四店、订单状态900与日期范围，合并 `channel_type IN (自营其他,自营短视频)` 后按日汇总单量和实付金额，两个子渠道不分别重复累计。客单价为合并后的实付总额/单量总额，GMV达成率以抖音商城预期为分母；月/总计同步聚合，实际汇总包括商城、自播及下述达人渠道。

抖音达人实绩：指定四店、状态900，合并 `channel_type IN (达人短视频,达人直播间,达人其他)` 按日汇总。该组合对应抖音达播，GMV达成率以抖音达播预期目标为分母。三个实际渠道互斥，底部实际GMV及单量合计现包含自播、商城、达播全部三组；pending_channels为空。

## 表格加载性能

页面使用compact总览（GET /api/expected-gmv?compact=true）只取来源、版本和日期索引，所选版本通过GET /api/expected-gmv/runs/{id}按需读取结果，历史明细和快照仍完整保留。前端按不可变版本ID缓存已读取结果，切换历史/店铺时复用已加载明细；手动填报跟随天猫日期可使用索引，无须下载天猫明细。

服务端请求内read_batch只反序列化一次同类型历史，写入使缓存失效；缓存不跨请求，避免默认单量及跟随同步变成陈旧数据。实际指标请求在页面内合并并复用30秒，点击刷新或重新读取实绩可强制更新；已完成AI任务不持续轮询。

渠道目标展示和手动填报表使用原生表格替代按列/单元格创建大量组件，保留日期列、首列固定、预期/实际配色、底部合计与原值提示。数字使用复用的Intl.NumberFormat。营销节奏页按需挂载。校验包含test_gmv_loading.py（读取复用与失效、摘要/详情历史一致）、test_gmv_table_render.mjs（1525单元格、日期覆盖、汇总和样式类别）、原单量与解析测试。

## 天猫预估单量客单价与手填覆盖

“预估单量”视图提供“编辑/批量填充”窗口，五个渠道各保留预期GMV、客单价和预估单量三行，只允许编辑后两行。客单价由用户手填（最多两位小数且大于0），单量为非负整数；千位逗号先转数值，原表GMV不修改。无手填覆盖时单量按GMV/客单价四舍五入到整数，手填单量优先，0明确保留，清空覆盖恢复自动。编辑客单价会重算自动单量，不覆盖已手填的单量，来源有提示。

批量支持单渠道/全部渠道、指定起止日期，统一设值、加、减、按序粘贴（空格/换行/制表符）和清空。加减使用当前显示值（含自动单量）；缺失基数或结果无效/负值时整批拒绝，先预览再保存。批量调整不改动区间外或非选中渠道的数据。

API为GET/PUT /api/expected-gmv/runs/{run_id}/forecast-inputs，历史用GET的version参数读取。数据按source_id独立维护，引用GMV解析run_id，使用base_version防并发覆盖；每次保存新增forecast_input版本，保留归一化输入和后端独立计算的单量，不改变原解析和飞书快照。前端只在进入预估视图时读取填报数据，不扩大总览包体。服务端再次校验渠道、日期、精度、范围和手填/自动优先级。

验证：test_gmv_forecast_inputs.py（历史、并发、千位/0/清空/计算口径/跨来源拒绝），test_tmall_forecast_bulk.mjs（区间设值、加减及原子拒绝）、test_gmv_table_render.mjs（可编辑输入和自动来源提示）。


## 编辑窗口的上月货架历史参考

点击“历史参考（上月货架）”后，默认按当前批量区间的起始日期查询，可在参考面板切换规划日期。10月日期取9月历史；其他月份按前一个自然月（含跨年）取值。当前月和上月目标均直接复用主表已解析的“渠道目标-GMV / 货架-常规”日目标，GMV金额和源坐标与主表完全一致，并检查源坐标仍位于对应GMV区域及渠道行；不另取父级货架合计或渠道目标-销售。上月相同日期多次解析时取最新成功版本。

匹配条件为abs(上月日目标-当前日目标)/当前日目标 <= 10%，包含边界。全部符合条件的上月日期按差值绝对值升序、日期升序展示，不补入范围外日期。面板展示目标金额、源坐标/版本、差值、实际实付金额、实际单量、客单价以及样本有效性。无历史、无匹配或零目标分别提示。

历史实际数据严格按用户提供口径：ads_ofs_order_daily_summary，pay_date位于上月区间，store_name=薇诺娜天猫旗舰店，order_type=货架；按日SUM(order_count)和SUM(pay_amount)，不额外添加订单状态或平台过滤。实际客单价为每日汇总实付金额/每日汇总单量。单量中位数和算术平均数只用匹配且单量完整有效的日期，缺失不填零，实际0单计入；客单价除数0时显示空。

API：GET /api/expected-gmv/runs/{run_id}/history-reference?target_date=YYYY-MM-DD。只在用户点击参考时读取，不写入当前预测和填报。test_gmv_history_reference.py覆盖±10%边界、排序、主表货架-常规口径一致、父级合计不参与、指定实绩表及过滤、分行汇总后的加权客单价、0/缺失、中位数/均值、历史版本去重与无匹配不查询。
